Message stream

The message stream is everything inside the conversation scroller: user bubbles, grouped agent responses, the work each turn did, the answer and its rich parts. v3 keeps the entry reducers in lib/chat.ts and the grouping in ChatMessages. It adds message actions, a code block with controls, a folded work group that finally mounts RuntimeItem, an inline turn failure card, citations, file cards and tools for long chats.

Source of truth for today's values: chat-ui-schema.md §3. Target design: the stream boards in the v3 wireframe. Existing visual values come from truex-design-spec.html "4. Messages". Live requests (RequestCard, PlanApprovalCard, QuestionCard) and approval records (ApprovalRecordView) are specified in the Requests part. This part only fixes where they sit in a turn.

Rules for this part: text under 13px uses --ink-2. Filled buttons with light text use --accent-fg. Spacing, z-index and motion tokens (--sp-*, --z-*, --dur-*, --ease-*) come from the Foundations part. A turn means one user message plus every response group that shares its turnId. "Settled" means the turn is not active: !(running && isLastGroup).

Data model

The persisted Message and the display Entry union stay the source for every row. New fields are optional, so today's history keeps rendering. Each new field names the backend item that supplies it. Fields tagged derive are computed on the client from data that exists today.

Behavior

  • Stage 1 order is unchanged, including every applyChatEvent row in schema §3.1. kind:"item" entries are no longer dropped in grouping. They go to work.
  • Grouping: each user message starts a turn. Every other entry joins the previous non-user group with the same turnId, else starts a new response group. Thinking in a group merges into one ThinkingBlock (texts joined with \n\n).
  • Order inside a response group: meta, ThinkingBlock, WorkGroup, inline requests, answer messages, SourcesList, file cards, TurnFailureCard, AnswerActions, receipt, follow-ups.
  • Anchors: turn-{turnId} goes on the first response group of a turn. The usage receipt and AnswerActions go on its last group only.
  • addFailure places the entry by turnId. Source: the turn.completed or error event run through turnFailure(), with ErrorRef.turnId from the event. With no turnId it attaches to the latest turn. See TurnFailureCard.
  • Stage 3 order is fixed: splitSuggestions first, then splitVisualizations, then markdown. Both splitters are fence-aware (``` or ~~~, length-aware). CodeBlock and CitationChip run inside markdown, so a marker in a fence stays code.
  • Memoize buildTurns on entries and running, and messageParts per entry on text and streaming.

Acceptance

  • buildTurns puts a commandExecution item in work of its turn, not in a new group.
  • A [truex-visualization:<uuid>] line inside a code fence renders as code.
  • A late delta after message.final does not change text (replay protection kept).
  • A failure event with no turnId attaches to the last turn; with a turnId it attaches to that turn even if newer turns exist.
