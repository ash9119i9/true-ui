Requests and Needs you

A request is anything the agent cannot continue without: a tool approval, a question or a plan review. Today one RequestCard per pending request renders after <ChatMessages> in .thread, so it scrolls with the transcript. v3 docks the head request above the composer, leaves a placeholder in the stream where the turn paused, and folds each answered request into an audit row. A topbar tray, Needs you, gathers every item blocking the chat with one fix per row. Two or more open requests can be reviewed in one sheet.

Source of truth for today's values: chat-ui-schema.md §3.0.3, §3.0.4, §3.5, §3.7 and §7.3.8. The answer helpers in §2.14 (lib/request-input.ts) are reused unchanged; their coverage row lives in the Composer part. Target design: design/.cv3-parts/requests.html. In this section page means Home in frontend/app/page.tsx, and pending means the page's list of open PendingRequests.

Hard facts that shape this part: buttons come only from options[] ({label, description}, no recommended flag). Plan approval is Approve or Revise. On expiry a non-secret question continues with its first option, while approvals and secret questions are declined. PendingRequest has no turnId, createdAt or threadId today (BE-02). Plans and secrets always ask, in every approval mode. Contrast: text under 13px uses --ink-2; filled buttons with light text use --accent-fg.

PendingRequest, ApprovalRecord and derived views

existsbackendP1 shared/contracts.ts · lib/request-input.ts · lib/approval-mode.ts · new lib/requests.ts (derive helpers)

The contract types stay as they are. BE-02 adds three optional fields to PendingRequest. Every rule below has a fallback for when they are absent, so P1 ships without them.

Data

// shared/contracts.ts (exists, BE-02 additions marked)
export interface PendingRequest {
  requestId: string;
  method: string;                  // only "item/tool/requestUserInput" is rendered
  detail: Record<string, unknown>; // detail.questions: InputQuestion[]
  expiresAt: string;               // ISO; unanswered requests auto-resolve
  responseSchema: string | null;   // always null publicly
  turnId?: string;                 // BE-02: turn that paused on this request
  createdAt?: string;              // BE-02: ISO, when the runtime raised it
  threadId?: string;               // BE-02: helper thread that asked (absent = main agent)
}
export interface InputOption { label: string; description?: string; }
export interface InputQuestion {
  id: string;
  kind?: "toolApproval";           // MCP tool permission prompt
  header?: string;                 // "Permission needed" for tool approvals
  question: string;
  action?: string;                 // humanised tool name, e.g. "Create sales order"
  isOther?: boolean;               // allows free text
  isSecret?: boolean;              // masked input; answer never echoed back
  options?: InputOption[] | null;
}

// shared/contracts.ts (exists, unchanged)
export interface ApprovalRecord {
  requestId: string;
  at?: string;
  turnId?: string;
  outcome: "answered" | "auto" | "expired" | "interrupted";
  autoMode?: "readOnly" | "auto" | "grant";
  items: (
    | { kind: "toolApproval"; action?: string;
        decision: "allowedOnce" | "allowedSession" | "allowedChat" | "allowedAlways"
                | "declined" | "expired" | "interrupted" }
    | { kind: "question"; question: string; answer?: string; note?: string; secret?: true }
  )[];
}

// Answer payload (exists) → POST /api/sessions/:id/approvals/:requestId { result }
type AnswerPayload = { answers: { [questionId: string]: { answers: string[] } } };
// plan: { answers: { plan_approval: { answers: ["Approve"] | ["Revise", "user_note: <feedback>"] } } }

// lib/requests.ts (new, derive)
export type RequestKind = "tool" | "question" | "plan";
export interface RequestView {
  request: PendingRequest;
  questions: InputQuestion[];      // detail.questions, [] if not an array
  kind: RequestKind;               // plan: single question id "plan_approval"; tool: any kind "toolApproval"
  secret: boolean;                 // any question.isSecret === true
  expiryOutcome: "declined" | { continuesWith: string } | "server";  // see Expiry rule
  orderKey: number;                // Date.parse(createdAt) if BE-02, else Date.parse(expiresAt)
  totalMs: number;                 // expiresAt − (createdAt ?? firstSeen), floor 1000
  anchorTurnId: string | null;     // turnId (BE-02) ?? seenTurn.get(requestId) ?? null
}
export function requestViews(pending: PendingRequest[], seen: SeenMaps): RequestView[]; // sorted
export function expiryOutcome(v: Omit<RequestView, "expiryOutcome">): RequestView["expiryOutcome"];

Behavior

  • detail.questions is unknown in the type. Parse it once in requestViews: keep entries with a string id and string question, drop the rest. A request with zero valid questions is not docked and not counted.
  • Sort order: orderKey ascending, then firstSeen ascending, then requestId. Until BE-02 the key is expiresAt, so the request that expires soonest leads. This is a stand-in for arrival order and is labelled "oldest first" only once createdAt exists. derive
  • expiryOutcome: kind === "tool" or secret → "declined". Otherwise, if the current question has options → { continuesWith: options[0].label }. Plan → { continuesWith: "Approve" }. A free-text-only question → "server" (copy stays generic). derive
  • msLeft(expiresAt, now) from lib/request-input.ts drives every countdown. Do not add a second timer.
  • firstSeen and seenTurn are filled on approval.requested and on history load. They are dropped when the request leaves pending. After a reload, firstSeen is the reload time, so the ring may start part-way: that is accepted until BE-02.

Acceptance

  • A request whose detail.questions is missing or not an array renders nothing and does not change the Needs-you count.
  • Two requests with expiresAt 10:30 and 10:25 dock the 10:25 one first. With BE-02 createdAt present, the earlier createdAt leads regardless of expiresAt.
  • The answer payload for a tool approval sends the original option label ("Allow"), never the display label ("Allow once").

Request cards

All three cards share today's internals: useExpiry(expiresAt) on the shared 1s clock (useClock), answerErrorMessage for send errors, and p.request-error[role=alert] + <ErrorRef> for failures. v3 moves submit state into one hook so the dock, the compact form and the batch sheet share it.

// components/v2/use-request-answer.ts (new, derive)
function useRequestAnswer(view: RequestView, onAnswer: (value: unknown) => Promise<void>): {
  sending: string | null;          // label of the pressed button, or null
  error: { message: string; ref?: ErrorRefData } | null;
  locked: boolean;                 // sending || expired || frozen || readOnly
  submit(payload: AnswerPayload, pressed: string): Promise<void>;
};
// submit: guards double-press (sending !== null → no-op), calls onAnswer,
// on reject sets error = answerErrorMessage(status). 409/404/410 also mark the
