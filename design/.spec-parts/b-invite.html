Form logic

Rules as coded

const clean    = (s) => s.trim().replace(/\s+/g, " ");
const initials = (n) => n.split(" ").filter(Boolean).map(w => w[0]).slice(0, 2).join("").toUpperCase();
const isValid  = (n) => n.length >= 2 && /\p{L}/u.test(n);
  • Whitespace: clean() trims the value and collapses runs of whitespace into one space. It runs on every input event and on submit. The cleaned value is the one sent and displayed.
  • Validity: the cleaned name must be at least 2 characters long (UTF-16 length) and contain at least one Unicode letter (\p{L}). "A1" is valid. "12" and "--" are not.
  • Initials: take the first character of each of the first two words and uppercase them. "alex rivera jones" gives "AR". "Cher" gives "C".
  • Input limits: maxlength="60", autocomplete="name", required. The form uses novalidate, so all validation is in JS.
  • Input events are ignored when the state is not valid, while busy, or after joining.
  • Submit is ignored while busy.
  • First name in the joined banner is name.split(" ")[0], passed through escapeHTML, which escapes & < > " '. Only this banner is built with innerHTML from user input. Every other place uses textContent. In production, render with the framework's text binding and skip innerHTML.

Profile specimen aura hash

const AURA      = ["--ice-dot", "--mint-dot", "--butter-dot", "--peach-dot", "--lilac-dot"];
const AURA_SOFT = ["--ice", "--mint", "--butter", "--peach", "--lilac"];

const h = [...name].reduce((a, c) => (a * 31 + c.charCodeAt(0)) >>> 0, 7);
const a = h % 5, b = (a + 1 + (h >> 4) % 4) % 5;
// --a1 = var(AURA[a]), --a2 = var(AURA[b]), --a3 = var(AURA_SOFT[a])

Tint values: --ice #EAF5F8 / --ice-dot #3691CD, --mint #E7F4ED / --mint-dot #A9D5BE, --butter #FFF3D9 / --butter-dot #EBCB8B, --peach #FBE9DD / --peach-dot #F0B999, --lilac #EFEDF8 / --lilac-dot #C4BDE3. These are fixed and have no dark variant. The empty-state fallback is butter-dot / peach-dot / butter.

Bug in the prototype: h is an unsigned 32-bit value, but h >> 4 is a signed shift. When h >= 2^31 the result is negative, so b can equal a or become negative (for example AURA[-2] is undefined, which gives var(undefined)). Use (h >>> 4) % 4 in production. This keeps b in the range 0 to 4 and different from a. If the hash also drives the real profile color, compute it in one shared place so the invite and the app agree.

Accessibility announcements

  • <p class="sr" aria-live="polite" id="live"> receives: each submit phase label, "Joined Northwind Labs", and "Opening Northwind Labs".
  • Nothing is announced when the invite request is sent or when the name error appears. The error is linked to the input through aria-describedby and focus moves to the input. Consider announcing "Request sent" as well.
  • The progress bar updates aria-valuenow (0 to 3).
  • prefers-reduced-motion: reduce cuts every animation and transition to .01ms.

Production wiring

The prototype hard-codes the following. Developers need to implement each item.

  • Invite token lookup: inviter name, title and avatar tint; workspace name and logo initial; role; sent date; expiry; invited email; and whether the signed-in user is already a member. This lookup decides the page state (valid, expired, member, invalid).
  • Accept endpoint: replaces the three 700ms fake phases. Keep the phase labels as progress feedback, but tie completion to the response rather than a timer.
  • Request-new-invite endpoint: backs "Request a new invite" in the Expired state.
  • "Switch account": in the prototype it only calls preventDefault(). It should sign the user out and return to sign-in with the invite token kept (for example as a returnTo param).
  • Terms link: href="#" today. It needs the workspace terms URL.
  • "Open Northwind Labs": today it only changes the label to "Opening…". It should navigate to the workspace (the first conversation, per phase 3 copy).
  • Expiry pill: "Expires in 6 days" and "Expired Sep 23" are static. Derive them from expiresAt and server time (send serverNow so client clock skew does not matter). The "Invites last 7 days" copy should come from the invite TTL.
  • Mock data mismatch: the sub line says "sent Sep 24" while the expired copy says "expired on Sep 23". Real data will not have this problem, but QA should not copy these dates as fixtures.

Proposed payload types

Proposal only. These types do not match any existing API. Align names with the backend before building.
// PROPOSAL - not an existing API
type InviteStatus = "valid" | "expired" | "revoked" | "invalid" | "already_member";

interface InvitePayload {
  token: string;
  status: InviteStatus;
  workspace: {
    id: string;
    name: string;            // "Northwind Labs"
    logoInitial: string;     // "N"
    memberCount: number;     // used by the board ("+11 teammates")
  };
  inviter: {
    id: string;
    name: string;            // "Maya Chen"
    title?: string;          // "Head of Research"
    avatarTint?: "ice" | "mint" | "butter" | "peach" | "lilac";
    isAdmin: boolean;        // shows the verified badge
  };
  role: "member" | "admin" | "guest";   // role pill text
  invitedEmail: string;      // "alex@northwind.dev"
  sentAt: string;            // ISO 8601
  expiresAt: string;         // ISO 8601
  serverNow: string;         // ISO 8601, for the countdown
  viewer?: {                 // present when signed in
    email: string;
    name?: string;           // prefill for the name field
    memberSince?: string;    // for "member since Aug"
  };
}

interface AcceptInviteRequest {
  token: string;
  displayName: string;       // clean()ed, 2-60 chars, contains a letter
}

type AcceptInviteResponse =
  | { ok: true; workspaceId: string; redirectUrl: string; member: { id: string; displayName: string } }
  | { ok: false; error: "invite_expired" | "invite_revoked" | "invite_invalid"
        | "email_mismatch" | "already_member" | "invalid_name" | "rate_limited" };

interface RequestNewInviteRequest { token: string; }
interface RequestNewInviteResponse { ok: boolean; notifiedInviter: boolean; }
