Conversation v3 plan

r2 is a strong base. It gets progress, approvals and usage right. Three kinds of work turn it into the page customers live in: correct the boards that promise data we don't have, draw the daily-use surfaces r2 skipped, and add the safety nets that hours-long sessions need.

Sources: chat-ui-schema.md §1–8, design/convo-v2-wireframe-r2.html (7 sections), and a scan of current agent chat products (Cursor 3, Linear agents, ChatGPT, Claude, Copilot, Perplexity). Section numbers below refer to the schema.

Where r2 stands

Keep

The placement rule (content inline, status pinned, diagnostics folded). Folded work groups with one live row. Requests docked above the composer with an audit row after. Receipt, trace waterfall, context ring. Plan history in the panel.

Correct

About 20 fields and states r2 draws that the contract doesn't have, like per-helper tokens, plan versions, a "recommended" option and "Thought for 4s". Also wrong mode labels, Esc order, request expiry copy and the visualization contract.

Add

No boards yet for the sidebar, ⌘K, empty state, attachments, @-mentions, message actions, code blocks, long-chat navigation, read-only viewers, streaming health, phone layout or accessibility.

Principles for r3

  1. One place for "what needs me". Pending requests, blocked goals, failed helpers and tools that need sign-in all roll into one count and one tray.

  2. Outcome first, mechanics on demand. Receipts say what happened and what to do next. Waterfalls, timing and model context stay one click away, or in developer mode.

  3. Every board states its data. Each board is tagged as existing data, derived on the client, or needing backend. Nothing new gets drawn from invented fields.

  4. Keyboard-first and calm. A global key reaches every action, Esc has one fixed order, and nothing jumps while text streams in.

  5. Edge states are real states. Read-only viewers, reconnecting streams, partial answers, phone width and screen readers each get a board.

§3.7 · §5.9

Cross-cutting

Accessibility and motion

  • Status live region. One polite region announces "Working", "Done" and "Approval needed". The streaming body never goes in a live region.
  • Reduced motion. Shimmer and pulse get static fallbacks, and transitions are also turned off.
  • Contrast. --ink-3 darkens to about #67757C. Text-bearing buttons fill with #2A72A3, since white on #3691CD is about 3.4:1. Bad flags use the error text token.
  • Focus. Messages get their outline back, the composer shows a ring on focus-within, and popovers trap focus.

Design system

  • Tokens. Spacing (2 to 40), z-index (base to menu-fixed) and motion (--dur-1..5, two easings), each taken from values already in the CSS.
  • One color vocabulary. r2's --ok/--bad alias the app's --success-*/--error-* names. Chart series tokens are added for both themes.
  • CSS. Legacy-only surfaces port to styles/v2 one PR at a time. Then the duplicates go, and Tailwind is either adopted or dropped.
  • Icons. Nine new v2 icons at stroke 1.75 replace lucide in 11 files.

Responsive boards

  • At ≤900px the panel becomes a drawer. At ≤720px one drawer shows at a time and the dock becomes the bottom bar.
  • The composer bar collapses into one overflow button.
  • A docked request card still fits with the phone keyboard open (fitPanel).

Bugs to fix alongside

  • HelperChip "View" targets .helper-group, but the rendered class is .hcard.
  • The sidebar Agents link never becomes active. /help leaves out /agents.
  • Share does nothing. UserMenu has no name or sign-out.
  • RuntimeItem, ProjectSidebar, ConnectedTools and Capabilities are never mounted.

How r3 gets built

It reuses r2's approach: section fragments joined by a stitch script into design/convo-v3-wireframe.html, with one sub-agent per fragment working in parallel. Each fragment ends with a data-status table like the one above.

Decisions needed before building

Fidelity

Keep r2's annotated wireframe style, or move r3 to high-fidelity screens built with the real tokens? Recommendation: stay in wireframe style and add one high-fidelity hero board for the main chat view.

Where model and agent live

Chips in the composer (recommended, so they're one tap away and visible before sending), or r2's status pill popover? The pill keeps the detail view either way.

P3 in r3

Draw checkpoints, citations and the canvas now so the layout leaves room for them, or leave them out until the backend commits?

Developer mode scope

Should the waterfall and masked privacy samples be developer-only, with every customer seeing the plain-language receipt and privacy actions?
